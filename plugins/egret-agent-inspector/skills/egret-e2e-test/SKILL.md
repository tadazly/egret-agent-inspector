# Egret E2E 测试

## 流程

1. **明确范围**：确认测试的页面 URL、账号或前置状态、要覆盖的流程和通过标准。缺少会影响结果的信息时再询问。
2. **探索**：按 `egret-game-operation` skill 手动走一遍流程，记录每一步使用的定位条件（优先 `id`）和预期出现的界面。
3. **编写用例**：把流程写成 `egret_run_steps` 的 JSON 用例，格式见 [references/test-case-format.md](references/test-case-format.md)。每个操作后都要有 `waitFor` 或 `assert`。
4. **运行**：用 `egret_run_steps` 执行。用户需要保存用例时，写入其项目中的 `e2e/<用例名>.json`，之后用 `file`（绝对路径）重新运行。
5. **排查失败**：根据失败步骤的 `error` 和附带截图判断是产品缺陷、用例问题还是环境问题。用例问题修正后重跑；不要为了通过而放宽断言或删除步骤。
6. **报告**：先给结论，再列出每个用例的 PASS/FAIL、失败步骤、实际与期望差异和截图结论。只报告实际执行过的结果，未执行的标记为 NOT TESTED。

## 编写原则

- 定位条件使用稳定的 `id`、精确文本或图片 `source`，不依赖 `hash`、坐标或 `index`（列表项等确实需要时除外）。
- 用 `waitFor` 等待状态；打开带动画的面板后加 `stableMs`，避免在动画过程中点击或拖动。
- 每个用例从明确的起点开始（`navigate` 或关闭残留弹窗），不依赖上一个用例的结果。
- 会产生真实消耗的操作（购买、发送、删除等）只在用户确认的测试环境和账号中执行。
